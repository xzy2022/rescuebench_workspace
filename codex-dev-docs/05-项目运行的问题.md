# 项目运行问题记录

ID：RUN-001：AutoDL 中 Unreal 拒绝以 root 用户启动
- 问题：Unreal 环境包下载、SHA-256 校验和解压均通过，但运行单点随机测试时 UnrealCV 无法连接 `127.0.0.1:9000`。直接执行 Unreal 二进制后显示 `Refusing to run with the root privileges.`。
- 分析：AutoDL 默认通过 root 用户操作，而 UE5 Linux 二进制内置了拒绝 root 运行的安全限制。项目原启动器将 Unreal 的标准输出和标准错误重定向到 `/dev/null`，因此最初只表现为 UnrealCV 端口连接被拒绝，掩盖了真实原因。
- 解决：创建锁定且禁止交互登录的专用用户 `rescue-runner`，加入 `video` 组；使用 ACL 只授予该用户穿过 `/root` 的权限，并授予 `/root/autodl-tmp/rescue-nomad/runs` 写入权限。新增 `/root/autodl-tmp/rescue-nomad/bin/rescue-run` 启动器，由 root 调用后通过 `runuser` 自动切换到 `rescue-runner`，再执行 Python 和 Unreal。
- 可能风险：不能再直接以 root 运行 RescueBench Python，否则 Unreal 仍会拒绝启动。重置 AutoDL 系统盘后，`rescue-runner`、`acl` 软件包、用户组和 `/root` ACL 都需要重新配置；数据盘中的 Unreal 环境、启动器和实验输出仍会保留。


ID：RUN-002：AutoDL 无桌面容器中的 Vulkan ICD
- 问题：切换到 `rescue-runner` 后，Unreal 已越过 root 检查，但仍在启动阶段退出；直接保留 Unreal 日志后发现 `vpCreateInstance` 返回 `VK_ERROR_INCOMPATIBLE_DRIVER`。
- 分析：服务器原有 `/etc/vulkan/icd.d/nvidia_icd.json` 指向 `libGLX_nvidia.so.0`，该库用于有桌面环境的 GLX 路径。AutoDL 容器采用无桌面运行模式，headless Vulkan 必须改用 `libEGL_nvidia.so.0`。CUDA、PyTorch 和 `nvidia-smi` 正常只能证明计算能力可用，不能证明 Vulkan 图形接口可用。
- 解决：安装 `vulkan-tools`，新增 `/etc/vulkan/icd.d/rescue_nvidia_headless.json`，将 ICD 库设为 `/lib/x86_64-linux-gnu/libEGL_nvidia.so.0`；`rescue-run` 自动设置 `VK_ICD_FILENAMES`、`HOME`、XDG 目录、`UnrealEnv` 和 `PYTHONPATH`。`vulkaninfo` 已识别 Tesla T4，单点随机测试成功连接 UnrealCV、获取观测并执行 829 步，最终在 180 秒因随机策略未完成第二阶段而返回 `TIMEOUT_PHASE2`；测试进程退出码为 0，说明运行环境正常。
- 可能风险：必须通过 `rescue-run` 启动，或手动设置相同的 `VK_ICD_FILENAMES`；缺少该变量时系统仍可能选中错误的 GLX ICD。随机 Agent 的任务超时属于基线策略结果，不应误判为 Unreal、Vulkan 或权限故障。重置系统盘后需要重建 headless ICD 文件并重新安装 `vulkan-tools`。


ID：RUN-003：推荐的服务器启动方式
- 问题：直接执行 Conda 环境中的 Python 不会自动切换用户，也不会设置 headless Vulkan 所需环境变量。
- 分析：非 root 用户、Vulkan ICD、用户 HOME、临时目录、Unreal 路径和 Python 模块路径必须保持一致；手动重复设置容易遗漏。
- 解决：统一使用 `"$PROJECT_ROOT/bin/rescue-run" "$ENV_PATH/bin/python" ...`。例如 Level 0 随机基线命令为：`"$PROJECT_ROOT/bin/rescue-run" "$ENV_PATH/bin/python" benchmark/experiment.py --model random --levels 0 --episodes 1 --no-collision --output "$PROJECT_ROOT/runs/random-baseline"`。可先执行 `"$PROJECT_ROOT/bin/rescue-run" id`，确认输出用户为 `rescue-runner`。
- 可能风险：`rescue-run` 当前固定使用 `/root/autodl-tmp/rescue-nomad` 作为项目根目录；若迁移项目或更改数据盘路径，需要同步修改启动器中的 `PROJECT_ROOT`、用户 HOME 和 Vulkan ICD 路径。


ID：RUN-004：NoMaD 官方权重无法从 Google Drive 下载
- 问题：`visualnav-transformer` 官方只在 Google Drive 提供预训练权重，但服务器连接 Google Drive 超时；`/etc/network_turbo` 同时提示当前 AutoDL 地区不支持官方学术加速。
- 分析：代码和 Python 依赖已经具备，NoMaD 适配器仍会因为缺少 `deployment/model_weights/nomad.pth` 而无法初始化。普通 `curl`、`wget` 以及启用当前地区的 AutoDL 学术加速都不能解决 Google Drive 的连通性问题。
- 解决：从固定提交 `maum-ai/CostNav_baseline@78b43f7aab6a287d40845260a0fceac3712ca7bd` 下载公开的 `baseline-nomad.pth`，通过 `hf-mirror.com` 获取后保存为 `/root/autodl-tmp/rescue-nomad/weights/nomad.pth`；校验 SHA-256 为 `494028c4edef232d9ab3f1f650b03a2f2fa4ca799503cb044564d988f3e9f769`。在 `visualnav-transformer/deployment/model_weights/nomad.pth` 建立符号链接，并将来源、提交、大小和校验值记录到 `manifests/nomad-weight.json`。真实 checkpoint 已在 Tesla T4 上完成加载和扩散推理测试。
- 可能风险：该文件来自第三方公开基线仓库，尚未与 Google Drive 官方文件进行逐字节比对。需要严格复现实验时，应在能访问官方文件后比较 SHA-256；若校验值不同，需要重新验证模型结构、推理输出和测评结果。


ID：RUN-005：后台任务中的 Python `-c` 参数引号被启动层处理
- 问题：首次通过后台任务执行 NoMaD 单点烟雾测试时，Python 报错 `NameError: name 'cuda' is not defined`，任务在加载 Unreal 前退出。
- 分析：多层 PowerShell、SSH、后台 shell 和 `python -c` 共同处理命令字符串，`device="cuda"` 中的引号在传递过程中被剥离，最终被 Python 解释为变量名。该错误与 CUDA、NoMaD 权重和 RescueBench 无关。
- 解决：不再把多行 Python 代码直接嵌入 `python -c`；先将脚本内容编码为 Base64，再通过 `echo <base64> | base64 -d | rescue-run python -u -` 从标准输入执行。重试后模型、UnrealCV 和状态机均正常运行。
- 可能风险：复杂命令继续使用多层内嵌引号时，字符串、路径和 JSON 参数仍可能被提前展开或截断。正式长期任务应优先使用仓库内的启动脚本；一次性诊断脚本使用 Base64 标准输入，并以后台日志中的实际命令输出为准。


ID：RUN-006：NoMaD 二阶段缺少担架目标图
- 问题：NoMaD 首次真实烟雾测试能够找到并抱起伤员，但适配器提示未找到二阶段 `stretcher` 目标图，只能把当前观测作为目标，最终在 `find_stretcher` 阶段超时。
- 分析：一阶段目标图由 `test_jsonl` 的 `reference_image_path` 提供；二阶段没有等价的内置参考图。`vint_agent.py` 会搜索 `topomaps/stretcher/level_<level>_<point_id>.png` 等文件，找不到时回退到当前观测。该回退可以避免程序崩溃，但不具备有效的目标导航语义，因此不能用于正式评分。
- 解决：根据 Level 0 的 25 个测试点配置，在 Unreal 中将观察者放到每个担架的实际接近方向并朝向担架，自动采集 25 张 320×320 BGR 图像。抽查 Point 0 后确认担架、救护车、颜色和视角正常；资产集中保存到 `/root/autodl-tmp/rescue-nomad/topomaps/stretcher/`，同时保存 `manifest.json` 和 `checksums.sha256`。重新测试时适配器已正确加载 `level_0_0.png`。
- 可能风险：这些目标图是根据测试点真实担架坐标生成的，属于评测先验资产；必须在实验报告中明确说明生成方法，避免与“完全未知环境探索”混淆。Level 1–4 尚未生成对应目标图，不能直接沿用 Level 0 资产。自动选择的接近视角也可能受墙体、障碍物或地图边界影响，批量生成后仍需抽查。


ID：RUN-007：现有 NoMaD 适配器没有实际使用拓扑节点
- 问题：指定 `--topomap-dir` 后，适配器会扫描并加载拓扑图，但 `_infer_nomad` 实际输入的 `goal_img` 仍是一阶段伤员参考图或二阶段担架目标图；加载的 `topomap_images`、`closest_node` 和 `goal_node` 没有参与节点定位、目标节点选择或模型推理。
- 分析：当前实现属于“语义目标图条件的 NoMaD 导航”，不是上游 `navigate.py` 中基于拓扑节点窗口进行距离预测、局部定位和子目标选择的完整流程。因此只有 `stretcher/` 目标图而没有 `images/` 拓扑节点时会出现 `No images found under .../topomaps` 警告，但当前直接目标图推理仍能运行。
- 解决：现阶段将 Level 0 结果明确标记为“语义图像目标条件的 NoMaD 测评”，不伪造拓扑节点来消除警告。Level 0 的正式 25 点任务使用参考图和担架目标图运行，并逐局写入 JSONL。
- 可能风险：该结果不能直接宣称为官方拓扑导航版 NoMaD。进入 Level 1–4 前需要裁决：继续采用当前直接目标图协议，还是采集各地图拓扑图并修改适配器，使其实现官方的节点局部化和子目标选择。两种协议的先验信息和任务难度不同，结果不应混合比较。
